§ 1

Context

AIKOQL agent knowledge runs on a write-mixed load — ingestion, object creation, context compilation, relationship traversal; point reads are frequent but only one of eight certified shapes. The system targets bounded-RAM agent hosts, bounded restart time, and a future where sharding or replication must not force a format rewrite: the identity/placement spec (logical-id-physical-id.md §53) separates what an object is from where a copy lives.

§ 2

The four candidates

aikoql v1 — WAL + RAM mirrordead end

Every write appends to one WAL and applies into an in-memory BTreeMap; the RAM mirror is the store. Measured price: open replays the whole WAL at 3.8 ms/MB (open of 100 MB = 376.7 ms) with an 8.77× peak-RSS multiplier. Unbeatable warm reads — zero disk by design — and a ceiling: no dataset-larger-than-RAM capability, unbounded WAL growth, linear replay, no compaction. The W8 p99 (31.2 ms) shows the ungrouped per-commit fsync.

redb — copy-on-write B-treecapped by design

Single-file MVCC B-tree, 4 KiB pages, transactional commits; recovery is open-the-file. Warm point reads are its home turf (18 µs W1 — 4 KiB pages vs v2's 64 KiB blocks is the whole story). And it is structurally capped at everything else: 2.0× the disk of v2 at 100K, 2.8× slower ingestion (494 vs 1,373 ops/s), 33× worse mixed-write p99 — every commit pays full COW + fsync. No compaction, no identity or placement concept, no sharding path in a single-file format. Its 32 ms write tail is not a bug; it is the design's price, exactly as v1's replay is the mirror's.

RocksDB — C++ LSMreference, not adopted

Not measured in this repo — no backend exists, and no benchmark row is claimed. Architecture-only: v2 deliberately mirrors the industry LSM's shape (WAL + memtable, sorted runs, tiered compaction, bloom filters, block cache). What it would cost here: a C++/MSVC cross-compile in a pure-Rust codebase, duplicated cache memory, level-compaction stalls surfacing as p99 spikes, an order of magnitude more tuning surface — and the ObjectId → LogicalId → ReplicaId → PhysicalLocation hierarchy would sit on top as application code, not engine guarantees. The right reading: v2 is this application's Rust LSM, specialized to its actual data model — the best-practices pieces, none of the generality tax.

aikoql-v2 — segmented LSM with an identity/placement layeradopted

Group-commit WAL → memtable → immutable segments (bloom + block index + v4 dense cadence) → size-tiered compaction with relocation → identity/replica/placement directories with checkpoint-bounded recovery. Every cost axis is a tunable knob, not a design wall — the engine Config carries all of them: memtable bytes, durability mode, committer group window, block-cache bytes, L0 trigger, merge chunk, checkpoint budget.

§ 3

The honest scorecard

v2's wins are decisive on the axes this application actually lives on; its deficit is one axis, precisely measured, with named levers.

Wins vs redb

Ingestion 2.8×; mixed-workload throughput 6.0× with a 33× better p99 tail; peak RSS −17%; disk −65%; bounded open via the M40 checkpoint (75.0 ms vs 347.6 ms at 600K updates); dataset-larger-than-RAM queryability; a compile-time identity/placement model redb does not have.

Wins vs v1

Peak RSS −30%; disk −20%; mixed p99 32× better (978 µs vs 31,159 µs); ingestion at parity; bounded recovery (v1 replays the entire WAL); compaction exists (v1 has none); larger-than-RAM datasets possible (impossible in v1); placement-direct hot reads (M39 probe: 8852 s debug baseline → 3.15 s release — the same fix, both regimes measured).

The one deficit — warm point reads

6.00× v1 on W1, 5.48× on W2 — inside the amended ≤8× design gate with 1.2–1.5× headroom — and ~1.9× redb on W1. Root cause is measured, not guessed: one 64 KiB block fetch + soft-SHA-256 per cold get (~18.7 µs of the 33.5 µs get-wall), against redb's 4 KiB pages and v1's zero disk. This is the bounded-RAM trade, priced precisely.

Why the deficit is tunable, not architectural: the read path already walks memtable → placement-direct anchor → bloom → block index → bounded decode, and each stage has a shipped knob behind it — the M39 placement-direct dispatch cut the hot-key path 2,800× (O(run) → O(16) decode window), the M17 tiered path bounds segment walks, and block target, cache sizing and the batch API are named, measured levers. v1's replay and redb's write tail have no equivalent lever — they are the designs.

4.1 The hot read is placement-direct, not a scan

    let state = self.state.read().unwrap();

§ 5

Decision

ADOPT AikoQL Storage V2 as the forward storage engine.
  1. v2 is the strategic target and the default — ratified 2026-09-07 and shipped: a fresh db_path auto-creates aikoql-v2, the Python SDK defaults to backend = "aikoql-v2".
  2. v1 remains available as the read-hot / RAM-affordant profile via storage.backend = aikoql — auto-detection makes any direction of the switch safe.
  3. redb stays the opt-out compatibility backend, not a target — snapshots and pre-flip databases keep opening as redb.
  4. RocksDB is not adopted — the reference LSM; v2 is the application-specialized Rust realization of the same architecture.

The call rests on the axes the application lives on — write-mixed throughput, tail latency, bounded memory, bounded recovery, disk economy, and a data model that survives distribution — where v2 is at parity or decisively ahead, and on the one deficit axis being a measured, tunable trade inside the certified design gate rather than a design wall.

§ 7

Risks and honest limits

The warm-read gap stays ~6× v1 until levers 2–4 land. Deployments that are pure read-hot and RAM-affordant should stay on aikoql until then. This is stated, not hidden: the amended gate is a design gate, and the 09-01 NOT ADOPT record stands in history until this ratification superseded it.

RocksDB has no measured row here. The comparison against it is architectural; a rocksdb harness would be the honest way to convert that row from reasoning to evidence if it is ever wanted.

The default flip is compatibility-safe by construction. Only the missing-path arm changed; existing redb files and v1 WALs keep auto-detecting to their engines, pinned byte-exact by regression tests.
